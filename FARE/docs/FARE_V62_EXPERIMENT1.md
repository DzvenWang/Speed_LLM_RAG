# FARE v6.2 — Experiment 1: Transfer Feasibility and Alignment (decision pilot)

This project is a **standalone Experiment 1 implementation integrated into the complete FARE source tree**, not a v6.2 end-to-end C1/C2/C3 formal model. Do not report the pilot as a final TRC benchmark.

## Non-negotiable reproducibility contract

- Train a new Support-only adapter from random FARE weights. `support_best.pt` contains this *same-run* training result and the original frozen STLAformer parameters; no `v5/v6 best.pt` is imported.
- Reuse **only** the existing `external_oos_paired` schema-6 OOF memory and the original frozen STLAformer checkpoint from earlier work.
- A single immutable `CandidateBank` is generated **after** Support-only training and contains the identical historically legal episode IDs for T0/T1/T2/T3. CandidateBank is generated by the frozen same-run retriever and may contain no usable episodes for early chronology.
- All four Transfer variants start with the same Support-only weights. Their Transfer parameters start afresh from a fixed seed and use the same optimizer, data, candidate scores, loss and validation windows. The selected variant is **never** chosen using Test labels.
- No query-only additive correction is present in the Transfer head; the new correction depends multiplicatively on historical candidate deltas. No legal candidate means final forecast == Support-only.
- Existing FARE v6/v6.0.1 checkpoint formats are not loaded by this pipeline. It does not modify original OOF files or historic experiment directories.

## Variants

| Variant | Model changes | What it isolates |
| --- | --- | --- |
| `direct` (T0) | Completed OOF residual of the historical **same node**, trained 12-step strength | Minimal residual-correction baseline |
| `legacy` (T1) | Original `PropagationTransport` unchanged, 3-channel evidence mix | Existing FARE Transport |
| `source_aligned` (T2) | Spatially aggregate `(source future - source last actually observed historical state)` **before** mixing paths. No source observation -> invalid. | Remove cross-node level-reference contamination |
| `candidate_aligned` (T3) | T2 + candidate-specific spatial-path logit and candidate-specific temporal lag logit | Whether each historical episode needs separate path/lag alignment |

All models apply evidence to the **frozen Support-only reference**, not to the bare backbone. T2/T3 preserve the same residual/failure streams, except corrected evolution calculation.

T3 is intentionally initialized with zero additive candidate-alignment logits so it begins with T2's alignment and learns candidate-dependent deviations. Its new pathway gradient is covered by tests. Lag remains bounded to 0..3 steps. Static directional graph weights are affinities, not measured road distances or physical propagation speeds.

## Stage order

1. **Foundation** (`--stage foundation`): train Support-only on the **full training set** for 6 epochs; save best checkpoint. Freeze it, build a single CandidateBank on 12,000 spread Train + 2,000 spread Validation windows, then run an **untrained** T0 direct-residual feasibility diagnostic with NULL and fixed α oracle.
2. **Transfer variants** (`--stage transfer --variant NAME`): for each T0/T1/T2/T3, independently optimize 4 pilot epochs on the identical Train subset while freezing Support-only; evaluate on the same fixed Validation subset. No retrieval ranker or Risk Gate is trained.
3. **Assess** (`--stage assess`): generate paired time-block bootstrap comparisons, official-unit and normalized MAE/RMSE, masked metrics and candidate-identity shuffling. Results: `experiment1_table.csv`, `experiment1_verdict.json`, candidate and variant manifests. This stage is CPU only and can run from a Gadi login node once all results are present.

**Scientific interpretation:** The per-horizon/per-node candidate+alpha oracle with NULL can look at Validation future *only to measure headroom*. It is an intentionally optimistic, non-deployable diagnostic upper bound. It is never used for training, checkpoint selection, model inference or final Test forecasting.

**Decision gate:** T3 must improve upon the best T0/T1/T2 with a positive 95% paired time-block CI, pass the matched candidate-identity shuffle check, and show positive NULL-inclusive oracle headroom. At least 512 Validation queries and 10 time blocks are required. Otherwise `INVESTIGATE_TRANSFER`; C1/C2/C3 remain `INCONCLUSIVE` regardless of pilot gain.

## Gadi resource defaults

- gpuvolta, 1×V100, 12 CPU cores, 32 GB memory, 48-hour job limit
- `config`: `FARE/configs/experiment1.yaml`; `seed=10`; `History=12`, `Horizon=12`
- Full Support: batch 32, 6 epochs
- CandidateBank: batch 16, 12k/2k spread subset
- Transfer: batch 8, 4 epochs each variant, fixed candidate set, GPU evidence table cache within 5 GiB
- **Smoke** uses 12 Train, 8 Validation and 1 epoch; requires actual STLAformer vendor, actual Benchmark cache and paired OOF memory; it is not a synthetic data substitute.

**Do not swap the FARE source directory while a PBS job from this version is running.** Use the same code for foundation and all four variants. Ensure the earlier v6.0.1 audit jobs really have been cancelled before replacing FARE code.

## Known verification boundary

The included tests cover schema, state/gradient paths, empty candidates, causal candidate selection, strict checkpoint provenance, 4-variant training and assessment on tiny synthetic tensors. They do **not** demonstrate predictive gains on real traffic data and cannot validate V100 throughput. The first real GPU smoke is mandatory prior to foundation/variant jobs.
